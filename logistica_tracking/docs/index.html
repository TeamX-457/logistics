Logistica Tracking API

REST + WebSocket API for real-time delivery dispatch and GPS tracking. This reference covers every endpoint the mobile client consumes, the live event channels, and the object shapes returned by each call.

The API is organised around three roles — client (books deliveries), driver (accepts jobs and streams GPS), and admin (dispatches and resolves conflicts). Every endpoint is scoped to one or more of these roles.

Two transports work together, and both are required for a functioning app: HTTP for commands and queries, and WebSockets for anything live. Job offers, location updates, and delivery confirmations are pushed — never poll for them.

Interactive schema

A machine-readable OpenAPI 3.0 document is served at /api/schema/, and a Swagger UI console at /api/docs/. Point your codegen tool at the former to generate a typed client.

Base URL

All paths in this reference are relative to the deployment host.

https://<your-host>/api/

During local development the server runs on http://127.0.0.1:8000/. On a device or emulator, localhost refers to the device itself — see React Native setup for the host address to use instead.

Authentication

The API uses JWT bearer tokens. Registration and login both return an access / refresh pair; send the access token on every subsequent request. 

Authorization: Bearer <access_token>
TokenLifetimePurpose
access8 hours Sent on every request and on the WebSocket handshake.
refresh7 days Store securely; used to obtain a new access token.
Registration logs the user in

Both register endpoints return a full token pair on success, so there is no need to call login afterwards. Persist the tokens directly from the registration response.

Requests without a valid token receive 401. A valid token belonging to the wrong role receives 403 — see below.

Roles & permissions

A user's role is fixed at registration and returned on the user object. Role is enforced server-side on every request; a client token cannot reach an admin endpoint regardless of what the UI allows.

RoleCan do
client View own deliveries, confirm delivery on arrival, watch live tracking.
driver Set availability, accept job offers, push GPS pings, view own trips.
admin Create deliveries, dispatch to drivers, resolve accept conflicts, cancel jobs, manage users.

Ownership is checked in addition to role: a driver may only push GPS for a delivery assigned to them, and a client may only confirm their own delivery. Admin bypasses ownership checks but not role checks.

Errors

Errors return the appropriate HTTP status with a JSON body. Endpoint-level failures use a detail string: 

{
  "detail": "Job already taken."
}

Validation failures instead return per-field arrays:

{
  "username": ["A user with that username already exists."],
  "password": ["Ensure this field has at least 8 characters."]
}
Handle both shapes

A single error handler should check for detail first, then fall back to treating the body as a field-error map. Both are returned by the same endpoints depending on failure mode.

StatusMeaning
400Validation failed, or the action is invalid for the resource's current state.
401Missing, malformed, or expired token.
403Authenticated, but the wrong role or not the owner of the resource.
404Resource does not exist, or is not visible to this user.
409Conflict — the resource was modified by someone else first.
429Throttled. Registration is capped at 5/hour and login at 10/hour per IP.

Pagination

List endpoints are paginated at 20 items per page. Pass ?page= to advance. Responses are wrapped: 

{
  "count": 47,
  "next": "https://<host>/api/deliveries/?page=2",
  "previous": null,
  "results": [ /* … */ ]
}

When next is null you have reached the last page. Build "load more" from next rather than incrementing page and testing for an empty array.

Delivery lifecycle

A delivery moves through five states. Most endpoints are only valid in specific states, and calling them elsewhere returns 400.

StatusSet byMeaning
pendingAdmin creates deliveryAwaiting a driver.
acceptedDriver accepted, conflict window elapsedDriver assigned, not yet moving.
in_transitDriver's first GPS pingEn route. Set automatically — there is no explicit "start trip" call.
deliveredClient confirmsComplete. Trip summary generated.
cancelledAdmin cancelsTerminal. Only reachable from pending or accepted.

How job acceptance resolves

Acceptance is not first-write-wins. When a driver accepts, the server records the attempt and returns 202 Accepted immediately, then waits a short conflict window (1 second by default) for other drivers to tap the same job.

  • One driver accepted — assigned; that driver receives job_accepted.
  • Two or more accepted — nobody is assigned. Admin receives conflict_alert and resolves it manually.
202 is not confirmation

A 202 from the accept endpoint means "your attempt was recorded" — not that the driver got the job. The real outcome always arrives over the driver's WebSocket channel as job_accepted or job_taken. In a conflict, no event is sent at all until an admin resolves it, so the driver UI must show a pending state that a timeout can clear rather than waiting indefinitely.

This flag is visible to admin but does not currently filter who receives job offers — the notify endpoints reach all drivers (or all priority drivers) regardless of availability. Treat it as a status indicator, not a mute switch.

POST /api/deliveries/{id}/accept/ Driver

Records this driver's attempt to accept a pending delivery. Takes no request body.

Response 202

{
  "detail": "Your request is being processed."
}
Wait for the WebSocket event

This response only confirms the attempt was recorded. Listen on the driver channel for job_accepted (you got it) or job_taken (someone else did). See how job acceptance resolves.

Errors

403Caller is not a driver.
404No such delivery.
409Already assigned or no longer pending.
POST /api/deliveries/{id}/confirm/ Client

Confirms receipt. Flips the delivery to delivered, generates its trip summary, and broadcasts delivery_confirmed to both the tracking group and the assigned driver. Takes no request body.

Only the client who owns the delivery may call this, and only while it is in_transit. Returns 200 with the updated delivery.

This is the driver app's cue to stop GPS

There is no server-side kill switch for location pings. The driver app must stop its background GPS loop when it receives delivery_confirmed, or it will keep pinging a completed delivery and draining battery.

Errors

400Delivery is not in_transit — including when already confirmed.
403Caller is not a client.
404Delivery does not exist, or belongs to another client.

Tracking

POST /api/location/update/ Driver

Pushes one GPS reading for an assigned, active delivery. This is the driver app's background location loop.

Body

FieldTypeNotes
delivery_idintegerrequiredMust be assigned to the calling driver.
latitudefloatrequired−90 to 90.
longitudefloatrequired−180 to 180.

Response 200

{
  "detail": "ok",
  "status": "in_transit"
}

The returned status reflects the delivery's state after the ping. The first successful ping on an accepted delivery flips it to in_transit automatically — watch for that transition rather than calling a separate "start trip" endpoint, because none exists.

Recommended cadence: every 5–10 seconds

Every ping updates the live cache and broadcasts location_update to watchers immediately. Only about one ping per minute is persisted to the database for trip history, so a faster cadence costs little storage — but it does cost battery and mobile data. Pause pinging when the app is backgrounded if your product allows it.

Errors

400Delivery is not accepted or in_transit.
403This driver is not assigned to that delivery.
404No such delivery.
GET /api/location/{delivery_id}/latest/ Any role

Returns the most recent known position for a delivery. Use this to paint the map on first render, then switch to the tracking WebSocket for live movement.

Response 200

{
  "latitude": 6.4512,
  "longitude": 3.4011,
  "timestamp": "2026-08-01T09:31:07.902Z"
}
The response shape varies

Served from cache, the body contains exactly the three fields above. Served from the database fallback, it also includes id and delivery. Read the three guaranteed fields and ignore the rest — do not assume a fixed key set.

Access is ownership-checked: a client or driver may only read their own delivery. Admin may read any.

Errors

403Not your delivery.
404No such delivery, or no location recorded yet.

Trips

Trip summaries are generated automatically when a client confirms delivery. They do not exist before that point — requesting one for an in-flight delivery returns 404.

GET /api/trips/{delivery_id}/summary/ Client

Returns the trip summary for the calling client's own delivery.

Response 200

{
  "id": 18,
  "delivery": 41,
  "total_duration": "00:42:19.331000",
  "start_time": "2026-08-01T09:14:55.104Z",
  "end_time": "2026-08-01T09:57:14.435Z",
  "route_snapshot": [
    { "latitude": 6.4281, "longitude": 3.4219, "timestamp": "2026-08-01T09:14:55.104Z" },
    { "latitude": 6.4512, "longitude": 3.4011, "timestamp": "2026-08-01T09:15:58.220Z" }
  ],
  "created_at": "2026-08-01T09:57:14.502Z"
}
Parsing total_duration

Duration is a string in HH:MM:SS.ffffff form, and exceeds 24 hours as "1 02:03:04" (days, space, clock). Date will not parse it — split on : yourself, or prefer computing the difference between start_time and end_time, which are plain ISO-8601 timestamps.

route_snapshot is the persisted path — roughly one point per minute, not every ping the driver sent. It is well suited to drawing a polyline of the completed route.

GET /api/trips/{delivery_id}/driver-summary/ Driver

Same object as above, scoped to the driver who drove the delivery. Returns 404 if the calling driver was not assigned to it.

All users, paginated. Filter with ?role=client, ?role=driver, or ?role=admin.

PATCH /api/admin/users/{id}/deactivate/ Admin

Sets is_active: false, blocking future logins. No request body.

{
  "detail": "User deactivated.",
  "user": { "id": 7, "username": "james_d", "is_active": false, … }

Existing sessions survive

Deactivation blocks new logins but does not revoke tokens already issued. A deactivated user keeps working until their access token expires — up to 8 hours.

PATCH /api/admin/users/{id}/activate/ Admin

Reverses deactivation. No request body. Returns the same envelope with is_active: true.

POST /api/admin/priority/ Admin

Adds a driver to the priority list. Re-adding an existing driver is safe — it updates the entry rather than erroring.

POST /api/admin/priority/

{ "driver": 7 }

Returns 201 with the created entry.

DEL /api/admin/priority/{driver_id}/ Admin

Removes a driver from the priority list. Note the path takes the driver's user ID, not the priority entry's own id.

Returns 204 with an empty body on success, or 404 if that driver was not on the list.

POST /api/admin/deliveries/{id}/notify/all/ Admin

Broadcasts a job_request event for a pending delivery to every priority driver. No request body. 

{ "detail": "Broadcast sent to 4 priority drivers." }

The delivery must still be pending, otherwise 404.

POST /api/admin/deliveries/{id}/notify/everyone/ Admin

Same as above but reaches every registered driver, priority or not. Despite the name, notify/all/ is the narrower of the two — this one is the wider broadcast.

POST /api/admin/deliveries/{id}/notify/{driver_id}/ Admin

Pushes job_request to a single named driver. No request body. Returns 404 if the delivery is not pending or the target is not a driver.

POST /api/admin/deliveries/{id}/resolve/ Admin

Manually assigns a driver after a simultaneous-accept conflict. This is how a delivery stuck in conflict gets unblocked. 

POST /api/admin/deliveries/41/resolve/

{ "driver_id": 7 }

Returns 200 with the updated delivery. The chosen driver receives job_accepted with resolved_by_admin: true; the others receive job_taken.

Errors

400driver_id missing from the body.
404No such delivery, or that user is not a driver.
409Already resolved — someone else was assigned first.
POST /api/admin/deliveries/{id}/cancel/ Admin

Cancels a delivery and notifies the assigned driver (if any) plus anyone watching its tracking channel, both via job_cancelled. No request body.

Only valid from pending or accepted. A delivery already in_transit or delivered cannot be cancelled and returns 400.

GET /api/admin/trips/{delivery_id}/summary/ Admin

Returns the trip summary for any delivery, without the ownership restriction that applies to the client and driver variants.

WebSockets

Live behaviour depends on WebSockets. An app that only calls the REST endpoints will appear broken: drivers will not receive job offers, and clients will not see the vehicle move.

Connecting

WebSocket handshakes cannot carry an Authorization header from a mobile or browser client, so the access token goes in the query string: 

wss://<host>/ws/tracking/41/?token=<access_token>

Use wss:// against a deployed host and ws:// against a local server. Every message arrives as JSON in a consistent envelope: 

{
  "event": "location_update",
  "payload": { "delivery_id": 41, "latitude": 6.4512, "longitude": 3.4011 }
}

Switch on event; the shape of payload depends on it. All three channels are receive-only — sending messages to the server over the socket does nothing.

Close code 4403 means auth failed

The socket closes with 4403 if the token is missing, expired, or belongs to a user without access to that channel. Treat it as a signal to refresh the token and reconnect — not as a transient network error to retry blindly.

React Native setup

Reaching a local server

localhost inside an emulator refers to the emulator itself, not your development machine.

TargetBase URL
Android emulatorhttp://10.0.2.2:8000
iOS simulatorhttp://localhost:8000
Physical devicehttp://<your-LAN-IP>:8000

For a physical device the server must bind to all interfaces (runserver 0.0.0.0:8000) and your machine's IP must be in the server's allowed hosts.

A minimal client

const BASE = "https://<your-host>";

async function api(path, { method = "GET", body, token } = {}) {
  const res = await fetch(BASE + path, {
    method,
    headers: {
      "Content-Type": "application/json",
      ...(token && { Authorization: `Bearer ${token}` }),
    },
    ...(body && { body: JSON.stringify(body) }),
  });

  // 204 has no body to parse
  if (res.status === 204) return null;

  const data = await res.json();
  if (!res.ok) {
    // detail for endpoint errors, field arrays for validation errors
    throw new Error(data.detail ?? Object.values(data).flat().join(" "));
  }
  return data;
}

Subscribing to live tracking

function watchDelivery(deliveryId, token, onMove) {
  const ws = new WebSocket(
    `wss://<your-host>/ws/tracking/${deliveryId}/?token=${token}`
  );

  ws.onmessage = (e) => {
    const { event, payload } = JSON.parse(e.data);
    if (event === "location_update") onMove(payload);
  };

  ws.onclose = (e) => {
    if (e.code === 4403) return refreshTokenAndReconnect();
    scheduleReconnect();   // back off, then retry
  };

  return () => ws.close();   // call on unmount
}
Reconnect with backoff

Mobile connections drop constantly — on backgrounding, on network handover, on tunnel timeouts. Reconnect with exponential backoff, and on reconnect call latest location once to resync, since events emitted while disconnected are not replayed.

Integration checklist

  • Store access and refresh in secure storage, not AsyncStorage in plaintext.
  • Send role on login and route sign-in screens accordingly.
  • After accepting a job, show a pending state — wait for job_accepted, and time out rather than hanging.
  • Stop the GPS loop on delivery_confirmed and on job_cancelled.
  • Handle both error body shapes in one place.
  • Paginate via next, not by incrementing page.
  • Treat WebSocket close 4403 as re-authenticate, everything else as retry.
